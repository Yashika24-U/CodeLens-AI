1. The Core Concept: What is a Type?
In JavaScript, a variable can be a string, then a number, then an object. JavaScript doesn’t care. TypeScript demands that you declare what data type a variable is allowed to hold.

TypeScript
// Basic Type Assignment
let developerName: string = "Yashika";
let yearsOfExperience: number = 1.5;
let isFullStack: boolean = true;

// If you try to do this, TypeScript will stop you immediately:
yearsOfExperience = "two years"; // ❌ Error: Type 'string' is not assignable to type 'number'.
2. Objects and Interfaces (The Blueprint)
Since you are building a full-stack web app, you will constantly move data objects around (like a User or a Review). An Interface is just a checklist or blueprint for what an object must look like.

TypeScript
// Define the blueprint
interface User {
  id: string;
  username: string;
  email: string | null; // This means email can be a string OR null (Union Type)
  avatarUrl?: string;   // The '?' means this field is optional!
}

// Use the blueprint
const currentUser: User = {
  id: "uuid-1234",
  username: "yashika_dev",
  email: null, // Valid because of our union type
  // avatarUrl is missing, which is fine because it's optional
};
3. Typing Functions
When you write functions (like calling an API or filtering an array), TypeScript wants to know two things:

What are the types of the inputs (arguments)?

What is the type of the output (return value)?

TypeScript
// A function that takes a string argument and returns a Promise containing a User object

5. The "Survival Guide" Cheat Sheet for Your First Project
When you feel stuck, keep these three rules in mind:

Use Type Inference (Let TS do the work): You don't need to type everything. If you write const defaultStatus = "PENDING";, TypeScript is smart enough to know it's a string. You don't need to write const defaultStatus: string = "PENDING";.

Look at the Tooltips: Hover your mouse over any error underline. Read the last line of the error message—it usually tells you exactly what is missing or mismatched.

Let's break down exactly what each piece of React.Dispatch<React.SetStateAction<User | null>> actually means in plain English.

Breaking Down the Robotic Language
Let's unpack it piece by piece from the outside in:

1. React.Dispatch<...>
In computer science, Dispatch means "to send off a message or action." In React, a dispatch function is simply a function that sends a new value to React so it can trigger a re-render.

Plain English: "This is a function used to trigger a state update."

2. React.SetStateAction<...>
This describes how you are allowed to update the state. React allows you to update state in two ways:

Directly: setUser(newUser) (passing the value straight in).

Via a callback function: setUser((prevUser) => ...) (passing a function that takes the previous state).

Plain English: "You can update this either by passing a new value directly, or by passing a functional updater."

3. <User | null>
This is the Union Type you already know. It specifies the exact data that is allowed to live inside this state.

Plain English: "The data being managed must be either a valid User object, or it must be null."

Putting It All Together
If you translate the entire sentence from TypeScript into Plain English, it says:

"This is a function (Dispatch) that updates React state (SetStateAction). The only data it is allowed to accept as an update is either a User object or null."

1. Why TypeScript? (The Real Core Reason)
JavaScript is a dynamically typed language. This means it only discovers errors at runtime (when the user is actively clicking buttons on your deployed website).

TypeScript adds a static type system. It acts as a safety guard that scans your code at compile time (while you are typing in your editor).

Real Time Scenario:

his is where the magic of a shared type system between your backend and frontend comes into play.

When you build a full-stack web application using the PREN stack, you aren't just writing isolated backend and frontend code—you are defining a strict data contract.

Here is step-by-step exactly how TypeScript catches this error in your editor before it can ever break in production.

Step 1: The "Data Contract" (The Single Source of Truth)
In a professional full-stack project, you create an interface or a type file that represents your database schema. Let's say you have a file called types.ts that both your backend API routes and your React frontend components look at:

TypeScript
// types.ts (Shared Contract)
export interface UserProfile {
  id: string;
  username: string; // ◄ Look at this field
  email: string;
}
Because your React components import this UserProfile interface, TypeScript expects every component displaying a user's name to use .username.

Step 2: Without TypeScript (The Invisible Crash)
Imagine you change that field in your PostgreSQL database to userId and update your Express backend to return userId.

If you are using pure JavaScript on the frontend, your React component looks like this:

JavaScript
// ProfileCard.jsx (Pure JavaScript)
export default function ProfileCard({ user }) {
  return (
    <div>
      {/* The backend is now sending 'userId', NOT 'username' */}
      <h1>Welcome, {user.username}</h1> 
    </div>
  );
}
What happens?
Your Editor: Stays completely silent. No errors, no warnings. Everything looks fine.

The Build: It compiles and builds perfectly. You deploy it to AWS.

The Production Crash: A user logs in. The frontend looks for user.username, but it receives undefined. The screen either goes completely blank, shows a broken UI, or crashes with an error because the data it expected is missing.

Step 3: With TypeScript (The Instant Red Underline)
Now look at the exact same scenario, but your React component is written in TypeScript using that shared interface:

TypeScript
// ProfileCard.tsx (TypeScript)
import { UserProfile } from './types';

interface Props {
  user: UserProfile; // ◄ Enforcing the contract
}

export default function ProfileCard({ user }: Props) {
  return (
    <div>
      {/* ❌ TypeScript instantly underlines 'username' in RED! */}
      <h1>Welcome, {user.username}</h1> 
    </div>
  );
}
How your editor knows instantly:
The moment you change username to userId inside your central types.ts file, the original blueprint changes.

TypeScript running in the background of your editor (like Cursor or VS Code) constantly scans your open project files against their blueprints.

It immediately notices: "Wait a minute! ProfileCard is trying to read .username, but according to the UserProfile blueprint, .username no longer exists. Only .userId exists."

It throws a Compile-Time Error (a bright red underline) directly on the exact line of code that needs to be fixed.

The Ultimate Shield: It Blocks the Deploy
Even if you somehow ignore the red underlines in your editor and try to push your code to production, the build command (npm run build) will run a command called tsc (TypeScript Compiler).

tsc will scan the project, spot that a component is trying to read a field that doesn't exist, and instantly fail the build. It will refuse to create the final JavaScript files for deployment until you change .username to .userId in all 15 components.

This is how TypeScript ensures that if your backend schema changes, your frontend is structurally forced to change with it, completely saving you from accidental 
production crashes.


2. What Does It Do Under the Hood?
Browsers (Chrome, Safari, Edge) and execution environments (Node.js) cannot read or execute TypeScript code. They only understand vanilla JavaScript.

TypeScript is purely a development tool. When you run your build command (using Vite, Webpack, or tsc), TypeScript does two distinct things:

Type Checking (The Security Guard): It scans all your files for type mismatches, missing props, or invalid function arguments. If it finds an error, it stops the build.

Compilation/Transpilation (The Translator): Once everything is verified as safe, it completely strips away every single interface, type alias, and type annotation, translating your .ts or .tsx files into clean, ordinary .js files.

The Big Realization: Once your application is running in production, TypeScript is completely gone. There is zero performance penalty for using TypeScript because the browser only runs the pure JavaScript that was left behind.

You use undefined (or null) for some states because your frontend app starts running before your backend data arrives over the network.

Here is the exact real-world engineering reason why you do this, using your current project as a perfect example.

The Reality: Your App Has 3 States of Existence
Think about what happens the exact millisecond your dashboard loads in the browser. You have a state variable for the user's project history:

TypeScript
const [projectHistory, setProjectHistory] = useState<CodeReview[] | undefined>(undefined);
Why start with undefined instead of an empty array []? Because undefined means "We don't know the answer yet."

Here is how your system uses undefined to decide what to show on the screen:

1. State is undefined (The "Loading" State)
What it means: The page just opened. The frontend is currently firing an Axios request to your PostgreSQL database, but the server hasn't answered yet.

What you show the user: A loading spinner or a skeleton screen.

2. State is [] (The "Empty" State)
What it means: The backend responded! The request is complete, and the server said: "This user has zero code reviews saved."

What you show the user: A friendly message saying "You haven't submitted any code for review yet! Click here to upload your first file."

3. State is [ {...}, {...} ] (The "Success" State)
What it means: The backend responded with real data.

What you show the user: A beautiful table listing all their projects.

Why this matters in your code (Conditional Rendering)
If you initialized your state as an empty array [] instead of undefined, your app wouldn't be able to tell the difference between "We are still waiting for the backend" and "The backend says there is no data."

By using undefined, you can write clean layout logic in your React components like this:

TypeScript
if (projectHistory === undefined) {
  return <LoadingSpinner />; // Shows while waiting for the network
}

if (projectHistory.length === 0) {
  return <EmptyStateMessage />; // Shows when the user actually has no data
}

return <ProjectTable data={projectHistory} />; // Shows when data arrives
}
Summary Cheat Sheet
Initialize with a default value (like "" or []): If the starting state is safe to use immediately (e.g., an empty search bar input field).

Initialize with undefined or null: If the data must come from an API or database first. It acts as a flag telling your UI, 
"Wait, don't paint the final screen yet—we are still fetching the truth from the server!"
